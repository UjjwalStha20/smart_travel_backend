## How status codes were chosen

All codes were taken from the handler code paths in `app/routers/*.py`, then exercised
through the request + response models in `app/schemas/*`. Where the implementation is
asymmetric (e.g. `POST /users/` → 200, not 201; `POST /auth/register` with garbage → 201),
the suite asserts the implemented behavior rather than a hypothetical one.

## Endpoints deliberately left for manual verification

- **LLM paths without Ollama** — every `POST /chat`, `/trip-plans/{id}/messages`,
  content-regenerate endpoints, and auto-generated destination content needs `qwen3:8b`;
  they will 500 without it. Run with Ollama for full 369/369.
- **`POST /optimization/route` empty body (OPT-014)** — currently the resolver raises an
  uncaught `AttributeError` → 500. Documented instead of asserted.
- **`POST /auth/register` sloppy-validation cases (AUTH-005…010)** — asserts 201 or 422
  without pinning either, because the current handler accepts many invalid payloads.

## KNOWN API ISSUES (found during audit, reflected or documented in the suite)

1. **Public endpoints that arguably should require auth**:
   `GET /users/`, `GET /users/{id}`, `GET /user-trips/`, `GET /user-trips/{id}`,
   `GET /activity-logs/`. They leak PII/activity without any token. (`app/routers/user.py`,
   `app/routers/user_trip.py`, `app/routers/activity_log.py`)
2. **`POST /auth/register` performs no real validation** — empty `name`, empty `password`,
   duplicate-email handling is inconsistent (400 in `create_user`, 201 in register).
3. **`POST /users/` returns 200 instead of 201** (`app/routers/user.py`).
4. **Photo router injection differs from every other router** — written as
   `photo_service: PhotoService = Depends(lambda: PhotoService())` style with plain
   defaults (`param: X = None`); works, but is non-idiomatic and easy to break.
5. **Rate limits are strict and hard-coded**: register 3/min, login 10/min, chat 10/min.
   Fine for prod, but they force the suite to log in as seeded users rather than registering
   per test, and force 429-tolerant assertions.
6. **`POST /optimization/route` with an empty body → 500** (uncaught `AttributeError`,
   no multi-model support for null) instead of a clean 422.
7. **LLM dependency**: destination-content GET auto-generates via Ollama; without it the
   GET 500s. The response contract also varies (list vs dict) between endpoints.
8. **`Forgot/Reset password` flow**: `reset_token` is bytes token in `UserOrm`; reset uses a
   one-time token embedded in a signed URL — callers must extract `reset_token` from the 200
   response of `/auth/forgot-password` (`{{reset_token}}`), which the suite does.
9. **`GET /destinations/` stats** (`DEST-007`) calls the LLM generator for every candidate
   when no embeddings match — slow/500 without Ollama.

## Suggested next steps (project fixes, not test fixes)

1. Add `Depends(get_current_user)`/admin guard to the five public debug endpoints (issue 1).
2. Tighten `RegisterRequest` validation (min lengths, email format) so 422 is deterministic.
3. Normalize the photo router to standard FastAPI dependency injection (issue 4).
4. Add a fast-fail 422 for empty `/optimization/route` bodies (issue 6).
5. Document the external-service 502s (weather/flights/map) as expected degradation.
