SMART TRAVEL MANAGEMENT SYSTEM — COMPLETE UML ANALYSIS
=======================================================

1. PROJECT TITLE
----------------
Smart Travel Management System (Nepal)


2. PROJECT DESCRIPTION
-----------------------
A full-stack web application for planning and managing travel in Nepal. The
backend provides a RESTful API for CRUD operations on travel resources
(destinations, attractions, trekking routes, accommodations, food costs,
permits, reviews, photos) plus an AI-powered chatbot that answers
natural-language travel queries using OpenRouter's LLM. Users can browse
destinations, save favorites, plan trips with itineraries, and get
AI-assisted recommendations — all authenticated via JWT. The frontend
(separate Vite + React app) consumes the API.


3. PURPOSE OF THE SYSTEM
-------------------------
To centralize Nepal travel information (destinations, attractions, trekking
routes, costs, permits) and provide intelligent trip planning assistance
through an AI chatbot, making it easier for travelers to discover, compare,
and plan their Nepal adventures.


4. TECHNOLOGY STACK
--------------------

  Layer               | Technology
  --------------------+-----------------------------------------------
  Backend Framework   | FastAPI (Python 3.14+, ASGI)
  Frontend Framework  | React + TypeScript (Vite), separate repo:
                      |   Smart-Travel-Planner-Frontend/
  Database            | PostgreSQL with SQLModel ORM
                      |   (SQLAlchemy + Pydantic)
  Authentication      | JWT (python-jose + OAuth2PasswordBearer)
                      |   + bcrypt password hashing

                      |   10/min login)
  Testing             | pytest + httpx
  Server              | Uvicorn (ASGI)
  Package Manager     | uv (Python)


5. USER ROLES
--------------

  Role        | Privileges
  ------------+----------------------------------------------------------
  traveler    | Default role. Can manage own profile, trips, itineraries,
              | saved destinations, reviews, photos, chat conversations.
              | Read access to destinations, attractions, trekking routes,
              | etc.
  admin       | All traveler privileges plus create/update/delete any
              | resource (destinations, addresses, permits, etc.)


6. MAIN MODULES / FEATURES
---------------------------

  Module              | Description
  --------------------+---------------------------------------------------
  Auth                | Register, login, JWT token issuance, password
                      | hashing, current user endpoint
  User Management     | CRUD for users; profile editing
  Destination         | CRUD for attractions and treks with rich filtering
                      | (category, name, location, rating, permit)
  Address             | CRUD for location data (province, district, place,
                      | coordinates, altitude)
  Attraction          | CRUD for attraction-specific data (types, hours,
                      | duration), linked to EntryFee
  Trekking Route      | CRUD for routes with difficulty, distance, days,
                      | altitude, plus RoutePoints
  Route Point         | CRUD for waypoints on trekking routes (sequence,
                      | distance, hours, overnight, address, accommodation,
                      | food)
  Accommodation       | CRUD for lodging pricing (budget/standard/luxury)
  Food Cost           | CRUD for meal pricing (budget/standard/luxury)
  Entry Fee           | CRUD for attraction entry fees (Nepali/SAARC/
                      | Foreign categories)
  Permit              | CRUD for trekking permits (Nepali/SAARC/Foreign)
  Photo               | Upload/download photos (file validation: images
                      | only, 10MB max); static serving via /uploads
  Review              | CRUD for user ratings and comments on destinations
  Saved Destination   | Bookmark destinations
  User Trip           | Plan trips (pace, budget, duration, status)
  Itinerary           | Day-by-day trip breakdown
  AI Chat             | Natural-language Q&A powered by OpenRouter LLM
                      | with tool calling (10 functions across 5 tools)
  Health              | Simple health-check endpoint

11. BUSINESS LOGIC / WORKFLOW
------------------------------

  DESTINATION CREATION:
    1. Authenticate as admin
    2. POST destination data (address, attraction or trekking_routes
       nested)
    3. DestinationService.create_destination():
       a. Create/get address via AddressService.get_or_create_address()
       b. Create Destination with address FK
       c. If category == attraction: create Attraction + EntryFee
          records
       d. If category == trek: create TrekkingRoute + RoutePoint
          records
       e. Refresh and return full destination

  AI CHAT WORKFLOW:
    1. User sends message -> POST /chat/
    2. AIService.process_message():
       a. Load or create ChatConversation
       b. Save user message to DB
       c. Load last 30 messages as history
       d. Send to OpenRouter LLM with system prompt
       e. Parse response for <tool_call> tags
       f. If tool call found: execute tool, inject result as user
          message, re-prompt (up to 5 rounds)
       g. Save assistant reply to DB
       h. Return {reply, conversation_id}

  PHOTO UPLOAD:
    1. Validate file extension (jpg/jpeg/png/gif/webp)
    2. Validate file size <= 10MB
    3. Generate UUID filename, save to uploads/ directory
    4. Create Photo record with image_url = /uploads/{uuid}.{ext}
    5. Serve statically via FastAPI StaticFiles mount

  USER OWNERSHIP:
    - Users can only modify their own resources (reviews, photos,
      trips, itineraries, saved destinations, chat conversations)
    - Admin has full access override


12. SYSTEM STATES
------------------

  USERTRIP STATES:
    planned --> ongoing --> completed

  AUTH STATES:
    unauthenticated -> login/register -> authenticated (JWT)
    authenticated -> token expires -> re-authenticate

  CHAT PROCESSING STATES:
    receiving message -> loading history -> calling LLM
      -> [tool call detected] -> executing tool -> injecting result
         -> calling LLM (loop up to 5x)
      -> [no tool call] -> returning reply


13. TYPICAL USER FLOWS
-----------------------

  REGISTRATION:
    [Browser] -> POST /auth/register (name, email, password, role)
      -> Validate uniqueness (409 if duplicate)
      -> Hash password (bcrypt)
      -> Create User record
      -> Generate JWT (sub=user.id, exp=24h)
      -> Return {access_token, token_type: "bearer"}

  LOGIN:
    [Browser] -> POST /auth/login (email, password)
      -> Lookup user by email
      -> Verify password (bcrypt)
      -> Generate JWT
      -> Return {access_token, token_type: "bearer"}

  BROWSE + SAVE DESTINATION:
    [Browser] -> GET /destinations/?category=trek&province=Gandaki
      (unauthenticated OK)
      -> Filtered + paginated results
    [Browser] -> POST /saved-destinations/ (Auth: Bearer token)
      -> Create SavedDestination {user_id, destination_id}

  PLAN A TRIP:
    [Browser] -> POST /user-trips/ (Auth)
      -> Create UserTrip {user_id, destination_id, route_id,
                          pace, budget, dates}
    [Browser] -> POST /itineraries/ (Auth)
      -> Create day-by-day Itinerary entries for the trip

  AI CHAT:
    [Browser] -> POST /chat/ (Auth)
      {message: "What are the best treks in Nepal under 7 days?"}
      -> AIService dispatches to LLM
      -> LLM calls search_trekking_routes(difficulty="easy")...
      -> Tool result sent back to LLM
      -> LLM formulates human-friendly response
      -> Returns {reply: "...", conversation_id: "..."}
